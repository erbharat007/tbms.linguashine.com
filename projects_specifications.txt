# 13. MOST IMPORTANT — Working Structure

This is the core of the application.

The relationship should be:

```text
                    ┌─────────────┐
                    │    CLIENT   │
                    └──────┬──────┘
                           │
                           ▼
                    ┌─────────────┐
                    │    QUOTE    │
                    └──────┬──────┘
                           │
                    Quote Accepted
                           │
                           ▼
                    ┌─────────────┐
                    │   PROJECT   │
                    └──────┬──────┘
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
          FILES          JOBS        RECEIVABLES
                           │             │
                           ▼             ▼
                        VENDOR       CLIENT
                           │           INVOICE
                           ▼             │
                       PAYABLE          ▼
                           │          PAYMENT
                           ▼
                       VENDOR
                       INVOICE
                           │
                           ▼
                        PAYMENT
```

This is essentially the heart of Protemos. The official documentation explicitly describes **Project as the central object**, with files, jobs and client/vendor finances attached to it. ([Protemos Wiki][2])

# 15. Project → Jobs → Vendor

Example:

Client requests:

**English → Hindi Translation**

Project:

```text
Project #P-1001
        │
        ├── Source File
        │
        ├── Job #J-1001
        │       │
        │       ├── Vendor: Translator A
        │       ├── English → Hindi
        │       ├── 10,000 words
        │       └── ₹5,000 Payable
        │
        └── Job #J-1002
                │
                ├── Vendor: Reviewer B
                ├── Hindi Proofreading
                └── ₹2,000 Payable
```

This is where the **Workflow** becomes useful.

```text
Translation
     ↓
Review
     ↓
Proofreading
     ↓
QA
     ↓
Delivery
```

Protemos supports building consecutive job chains through the Workflow tab and predefined job-chain templates. ([Protemos Wiki][3])

# 16. Project → Client Finance

Suppose:

```text
Project Value = ₹15,000
```

Create:

```text
Project
   │
   └── Receivable
          │
          ▼
     ₹15,000
```

Then:

```text
Receivable
     ↓
Client Invoice
     ↓
Client Payment
```

Important: **Project and Invoice should NOT have a simple one-to-one relationship.**

One project can contribute receivables to multiple invoices, and one invoice can contain receivables from multiple projects. The Protemos documentation specifically describes this relationship. ([Protemos Wiki][2])

So database-wise:

```text
PROJECT
   │
   └──< RECEIVABLE >──┐
                      │
                      ▼
                   INVOICE
                      ▲
                      │
   ┌──< RECEIVABLE >──┘
   │
PROJECT 2
```

# 17. Project → Vendor Finance

Similarly:

```text
Project
   │
   └── Jobs
         │
         └── Payables
                │
                ▼
          Vendor Invoice
                │
                ▼
          Vendor Payment
```

Example:

```text
Project ₹15,000

Client Receivable       ₹15,000
                       ─────────
Revenue                 ₹15,000

Translator Payable       ₹5,000
Reviewer Payable         ₹2,000
                       ─────────
Total Cost               ₹7,000

Estimated Profit         ₹8,000
```

**Project → Receivable → Client Invoice → Client Payment**

**Job → Payable → Vendor Invoice → Vendor Payment**

**Project → Files + Workflow + Communication + Reporting**

### One important distinction for the quotation

I would **not** call this simply a "Protemos clone." In the SOW, I'd describe it as:

> **Web-Based Translation Management System (TMS) with CRM, Project Management, Vendor Management, Workflow, Financial Management, Client/Vendor Portals, Reporting and Third-Party Integrations.**

That gives you room to implement the same **business functionality and relationships** without making the quotation dependent on copying Protemos's UI.

Yes. For this system, I recommend designing the MySQL database around the **business relationships**, not around the menu structure.

The most important relationship is:

**Client → Quote → Project → Job → Vendor**

and the financial flows are:

**Project → Receivable → Client Invoice → Client Payment**

**Job → Payable → Vendor Invoice → Vendor Payment**

# 20. INVOICE ↔ RECEIVABLE

Do **not** simply add `invoice_id` to `receivables`.

Use a pivot table.

```sql
CREATE TABLE client_invoice_receivables (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,

    invoice_id BIGINT UNSIGNED NOT NULL,
    receivable_id BIGINT UNSIGNED NOT NULL,

    amount DECIMAL(18,2) NOT NULL,

    UNIQUE(invoice_id, receivable_id),

    FOREIGN KEY (invoice_id)
        REFERENCES client_invoices(id)
        ON DELETE CASCADE,

    FOREIGN KEY (receivable_id)
        REFERENCES receivables(id)
);
```

This allows:

```text
Project A → Receivable 1 ─┐
                          ├── Invoice #1001
Project B → Receivable 2 ─┘
```

# 28. FILE MANAGEMENT

Instead of creating separate physical tables for every type of file, use a polymorphic structure.

## `files`

```sql
CREATE TABLE files (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,

    uploaded_by BIGINT UNSIGNED NULL,

    fileable_type VARCHAR(100) NOT NULL,
    fileable_id BIGINT UNSIGNED NOT NULL,

    original_name VARCHAR(255) NOT NULL,
    file_name VARCHAR(255) NOT NULL,
    file_path TEXT NOT NULL,

    mime_type VARCHAR(150) NULL,
    file_size BIGINT UNSIGNED NULL,

    version INT DEFAULT 1,

    created_at TIMESTAMP NULL,
    updated_at TIMESTAMP NULL,

    INDEX(fileable_type, fileable_id),

    FOREIGN KEY (uploaded_by)
        REFERENCES users(id)
);
```

This allows:

```text
files
 ├── Client
 ├── Vendor
 ├── Quote
 ├── Project
 ├── Job
 ├── Invoice
 └── Message
```

without creating seven separate file tables.

# 38. Financial Calculation

The database allows us to calculate project profitability without storing a manually entered "profit".

Example:

```text
PROJECT #P-1001

Client Revenue
─────────────────────
Receivable 1     ₹10,000
Receivable 2     ₹ 5,000
                 ───────
Revenue          ₹15,000


Vendor Cost
─────────────────────
Job 1 Payable    ₹5,000
Job 2 Payable    ₹2,000
                 ───────
Vendor Cost      ₹7,000


Other Expenses
─────────────────────
Expenses         ₹1,000


PROJECT PROFIT
─────────────────────
₹15,000
- ₹7,000
- ₹1,000
────────
₹7,000
```

So:

**Project Profit = Receivables − Payables − Project Expenses**

This should preferably be calculated through queries/services rather than stored as a permanent value.

# 40. Final Recommended Table Count

For the **core MVP**, I would target approximately:

| Category              |            Tables |
| --------------------- | ----------------: |
| Authentication & RBAC |                 5 |
| Master Data           |                 8 |
| Clients               |               4–5 |
| Vendors               |               4–5 |
| Quotes                |               5–7 |
| Projects              |               5–7 |
| Jobs                  |               4–5 |
| Client Finance        |                 5 |
| Vendor Finance        |                 5 |
| Files/Communication   |               4–5 |
| Expenses              |                 2 |
| Templates/Settings    |               4–6 |
| Audit/Notifications   |               2–3 |
| **Total**             | **~60–70 tables** |

That is a reasonable size for a **serious Laravel/MySQL TMS**, rather than trying to squeeze the entire application into 15–20 tables.

### One architectural recommendation

I would **not copy the Protemos database 1:1**. Use Protemos as the **functional reference**, but build your own normalized schema around these three financial chains:

```text
CLIENT
   ↓
QUOTE
   ↓
PROJECT
   ↓
JOB
   ↓
VENDOR
```

```text
PROJECT
   ↓
RECEIVABLE
   ↓
CLIENT INVOICE
   ↓
CLIENT PAYMENT
```

```text
JOB
   ↓
PAYABLE
   ↓
VENDOR INVOICE
   ↓
VENDOR PAYMENT
```
